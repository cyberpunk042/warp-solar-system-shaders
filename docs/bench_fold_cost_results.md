# The cost of folding — decode latency + mode ON/OFF, reproducible run record

Generated by `python -m warp_compress.bench_fold_cost`. Answers two questions directly, with numbers, not
intuition: **does super-elastic cost more latency?** (yes), and **what's the conclusion on folding, mode on
vs off?** (it's a per-group opt-in — and folding is never free). This is the honest close on the M20
(grouped-delta) + M21 (super-elastic) CPU arc.

## 1. Decode latency by mode — folding is never free

Correlated 16×64×64 bank. Fold OFF = the weights are a resident array, so "decode" is identity (the floor).

```
mode                                   decode µs    vs OFF
fold OFF (resident array)                    0.2      1.0x
M20 grouped_delta                          165.3      939x
M21 super_elastic L2 (lossy)               570.8     3243x
M21 super_elastic L3 (lossy)               640.4     3639x
M21 super_elastic L3+resid (exact)         743.4     4224x
M21 super_elastic L6 (lossy)              1007.8     5726x
```

- **Super-elastic is the higher-latency mode** — ~4× grouped-delta's decode, and it scales with stack
  depth (L2 < L3 < L6). Each layer is another low-rank reconstruction summed into the output.
- Grouped-delta is the cheaper fold (one reference + a residual add), but still ~10²–10³× a resident read.

(Absolute µs are numpy-on-CPU and will vary per box; the **ratios** are the story.)

## 2. Mode ON vs OFF, by bytes — the per-group opt-in

```
correlated bank (experts / adapters / tied layers):
  baseline (independent per-tensor)     150913 B   1.00x
  M20 grouped_delta (lossless)           40968 B    3.68x  WIN
  M21 super_elastic exact (L3+resid)     81959 B    1.84x  WIN

independent dense layers (the model bulk):
  baseline (independent per-tensor)     150137 B   1.00x
  M20 grouped_delta (lossless)          138975 B    1.08x  marginal
  M21 super_elastic exact (L3+resid)    176616 B    0.85x  LOSE
```

On **correlated** structure, folding wins big. On **independent** bulk it collapses toward break-even
(marginal for M20, losing for M21). Against a *native-int8* baseline (`bench_model_fold`) M20 on independent
goes fully negative (0.72×) — the exact side of 1.0× is baseline-dependent, but the verdict is the same:
**don't fold the independent bulk.**

## 3. Super-elastic is an accuracy dial, not a ratio winner

From `bench_super_elastic`: stacking layers drives error toward zero (L1 err 0.51 → L4 err 0.005 → L6 err
0.000) but the atom grows (ratio 3.56× → 1.28× → 0.81×, i.e. past break-even by L6). Adding *rank* to a single
fold instead **plateaus** at err ~0.24 and never reaches zero. So super-elastic buys an accuracy a single
low-rank fold cannot — down to **bit-exact** with a final residual (L3+resid: lossless *and* still 1.45–1.84×
compressed). You pay for that accuracy in both depth-scaled latency and bytes.

## Conclusion (measured, CPU oracle)

| question | answer |
|---|---|
| Does super-elastic cost more latency? | **Yes** — ~4× grouped-delta, scaling with stack depth. |
| Mode ON, when? | **Correlated groups only** (experts / adapters / tied layers): M20 for ratio (~3.7×), M21 when you need the lossy→exact accuracy dial. |
| Mode OFF, when? | **The independent bulk** — folding is marginal-to-losing there and not worth the decode latency. |
| M20 vs M21? | M20 = cheap ratio workhorse; M21 = expensive accuracy dial (graceful degrade → bit-exact). |

**The open, GPU-gated question.** These are *standalone-decode* CPU numbers. The native-engine thesis is
**fused decode-in-GEMM** — decode *into* the matmul so the fold cost overlaps compute you already do, rather
than being a separate tax (the `Q-401-A` C ABI is specified in the sibling engine's `SDD-402`). Whether fusion
erases the latency gap measured here is the number that needs a GPU — it cannot be answered on this CPU oracle.

## Reproduce

```sh
python -m warp_compress.bench_fold_cost      # this record
python -m warp_compress.bench_super_elastic  # the accuracy-dial detail (§3)
python -m warp_compress.bench_model_fold     # the native-int8 baseline (§2 NB)
```
